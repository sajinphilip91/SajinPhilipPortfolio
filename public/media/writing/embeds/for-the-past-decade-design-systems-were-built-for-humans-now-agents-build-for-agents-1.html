Design systems built to serve both — natively

For the past decade, design systems were built for humans. Designers browsed them in Figma. Developers referenced them in documentation. That model worked well — until AI agents became a meaningful part of how products are built.

AI agents now write UI code, build screens, generate components. They consume your design system. But they were never designed for. The system lives in an external tool. The agent has to be told about it each time, has to interpret it, has to guess how visual decisions translate to code. The result is familiar: inconsistency that compounds with every generated screen.

"Design systems were built for humans to reference. The AI era requires design systems that agents can actually use."

This is not an argument against Figma or hosted design systems — those tools remain valuable for human collaboration and visual design. The argument is simpler: modern design systems need to support both humans and AI agents. Right now, most don't support agents at all.

The problem — and what changes

Without an agent-consumable system
Agent invents components from scratch every task
Tokens inconsistent across generated screens
Design drift compounds with every build
Manual correction required after each task
Figma and code diverge over time
With an agent-consumable system
Agent reads the library before every task
Tokens applied consistently — system enforces it
Screens become more consistent over time
Correction work reduces considerably
Code is the source of truth — always current

What it looks like — the three-layer model

Three structured files do most of the work. Each layer has a distinct role — and the agent reads all three before touching any UI.

1
Design tokens
src/styles/tokens.css
Every color, font, spacing value, and radius as CSS custom properties. Imported once. Available to every component in the project. No hardcoded values anywhere else.
↓
2
Component map
.agent/skills/ui/component-library.md
A structured index of every component: exact file path, all props with types and defaults, usage examples. This is what the agent reads before every UI task — the map of what already exists.
↓
3
Real component code
src/components/ui/
The actual working components — what every screen imports from. The single source of truth. Built once. Reused everywhere. Updated by the design system agent when the product evolves.
What I noticed in practice

Before structuring things this way, agents would regularly create variations of components that already existed — slightly different button styles, custom spacing that didn't match the system. After implementing the component map, reuse improved considerably. The output felt more like work from someone who knew the codebase.

Why this matters for design leaders

This is fundamentally a question of design governance in an AI-native environment. The implications extend well beyond technical architecture.

01 — Consistency
Consistency at scale

When agents build from a shared component map, consistency improves — not because anyone enforced it manually, but because the system itself guided the output.

02 — Debt
Reducing design debt

A large source of design debt in AI-assisted development is components generated rather than reused. The component map creates structural pressure to reuse.

03 — Onboarding
Faster onboarding

New developers, new agents, new team members — all can understand the design system through a single file. The component map becomes onboarding documentation.

04 — Governance
Design governance

When the design system lives inside the codebase, changes are tracked through version control. You can see when a component changed, why, and what screens were affected.

05 — Language
Shared understanding

The component map creates a common language between designers, developers, and AI agents. Same component names, same prop vocabulary — communication improves across the team.

06 — Speed
Quality at speed

The promise of agentic development is speed. The risk is quality degradation. The design system is the structural mechanism that lets you increase speed without proportional inconsistency.

The strategic shift

Design leaders have always been responsible for maintaining the design system. In an AI-native team, that responsibility evolves — the system itself needs to be maintained in a format that agents can consume. That's a design leadership decision, not a technical one.

Before the architecture — the thinking

Everything you're about to see came from a deliberate architectural decision made before any code was written. Most teams skip this step. With agentic development, that compounds quickly — agents inherit whatever structure exists, good or bad.

Two agents. Separate responsibilities.

The most important structural decision: split UI work between two distinct agent roles.

Design system agent
Owns components · builds new ones · maintains the library · never builds screens
→
component-library.md
The shared map both agents read and the design system agent keeps current
→
UI developer agent
Builds screens · only consumes components · never creates them

This separation is what makes governance work. The design system agent is the gatekeeper — new components don't appear in the product without going through it. Every component that enters gets documented. The library stays accurate.

How to set it up

1
Create the folder structure

Create .agent/skills/ui/, .agent/rules/, .agent/agents/, src/styles/, and src/components/ui/. The separation between agent-readable and real code is the most important decision.

2
Define your design tokens

Create tokens.css with every color, font, spacing, and radius. Import once in main.jsx. From that point every component uses var(--token-name) — no hardcoded values anywhere else.

src/styles/tokens.css
3
Create the component map

Start with five components. Each entry: name, exact file path, props with types and defaults, one usage example. This is what the agent reads before every UI task.

.agent/skills/ui/component-library.md
4
Write the design system rules

The most important rule: read the component library before writing any UI code. Secondary rules cover token usage, file locations, and what to do when a component is missing.

.agent/rules/design-system.md
5
Create the design system agent

A dedicated agent file that owns all component creation and maintenance. Defines responsibilities, workflow, what it must read before starting, and what it must never do.

.agent/agents/design-system-agent.md
6
Build core components through the agent

Ask the design system agent to build each component against the token system. Button, InputField, Card, Badge, Modal — each added to the component map immediately after being built.

src/components/ui/
7
Add a live preview route

A single page rendering every component, every variant, every state — visible in the browser during development only. Agent updates it automatically when new components are added.

src/component-preview.jsx
8
Expose it for stakeholders

Point a subdomain at the preview route — behind authentication if needed. Stakeholders browse real rendered components. Same codebase, same deploy, no separate maintenance.

designsystem.yourdomain.com
